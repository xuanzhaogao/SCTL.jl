Fast multipole method

ParticleFMM evaluates the same particle sums as kernel_eval,

\[U(x_t) = \sum_{s=1}^{N_s} K(x_t - x_s)\, F_s, \qquad t = 1, \dots, N_t,\]

in $O(N_s + N_t)$ work instead of $O(N_s N_t)$. It wraps SCTL's ParticleFMM<double,3>, whose fast path is PVFMM, a kernel-independent FMM by Malhotra and Biros. SCTL.jl compiles PVFMM's headers into its library without MPI: the FMM runs in the Julia process, parallelized with OpenMP, and you need no MPI installation, no MPI.jl and no mpirun.

The same machinery gives BoundaryIntegralOp an FMM far field (see Boundary integral operators).

Supported kernels

fmm_supported_kernels()
8-element Vector{DataType}:
 Laplace3D_FxU
 Laplace3D_DxU
 Laplace3D_FxdU
 Laplace3D_Fxd2U
 Laplace3D_DxdU
 Stokes3D_FxU
 Stokes3D_DxU
 Stokes3D_FxT

For these kernels, SCTL.jl picks the FMM translation kernels that act on the equivalent densities:

  • Laplace kernels: the Laplace single layer for every translation.
  • Stokes velocity kernels: the Stokeslet plus a source term (Stokes3D_FSxU) for multipole expansions and the Stokeslet for local expansions.
  • Stokes3D_FxT (traction): the Stokeslet for every translation.

The other kernels have no FMM path and give an ArgumentError; use kernel_eval for those. The Helmholtz kernels, for example, need their wavenumber, which PVFMM does not pass to kernels.

Tutorial

One-shot evaluation

fmm_eval takes the same arguments as kernel_eval. Here are 10⁵ charges and 10⁵ targets:

Xs = rand(3, 100_000)
Xt = rand(3, 100_000)
F = randn(1, 100_000)

U = fmm_eval(Laplace3D_FxU(), Xs, F, Xt; digits = 8)

# check 100 targets against the direct sum
sample = 1:1000:100_000
Uref = kernel_eval(Laplace3D_FxU(), Xs, F, Xt[:, sample])
maximum(abs, U[:, sample] .- Uref) / maximum(abs, Uref)
4.474708617735532e-8

The first evaluation for a kernel and accuracy also precomputes PVFMM's translation operators and saves them in SCTL.fmm_cache_dir. Later evaluations, including those in new Julia sessions, load them from there.

Reusing points

A ParticleFMM object keeps its octree: the tree is rebuilt only when the points change. Solving an integral equation with gmres applies the operator to many densities on fixed points, which is exactly that fast case.

fmm = ParticleFMM(Stokes3D_FxU(); digits = 6)
set_sources!(fmm, Xs)
set_targets!(fmm, Xt)
set_density!(fmm, randn(3, 100_000))
t_first = @elapsed fmm_evaluate(fmm)        # builds the tree (and, the first time ever, the operators)
set_density!(fmm, randn(3, 100_000))
t_next = @elapsed U = fmm_evaluate(fmm)     # same points: tree and operators reused
@printf("first evaluation %.2f s, next %.2f s; U is %d × %d\n", t_first, t_next, size(U)...)
first evaluation 1.94 s, next 1.57 s; U is 3 × 100000

fmm_evaluate! writes into an existing array, and fmm_direct evaluates the same sum directly, which is useful for checking accuracy on small problems. Free the object with close(fmm), or leave it to the garbage collector.

Double layers and gradients

Kernels with source normals take them in set_sources!:

Xn = randn(3, 100_000)
U = fmm_eval(Laplace3D_DxU(), Xs, Xn, F, Xt; digits = 8)
Uref = kernel_eval(Laplace3D_DxU(), Xs, Xn, F, Xt[:, sample])
maximum(abs, U[:, sample] .- Uref) / maximum(abs, Uref)
1.5950574361124664e-8

Periodic boundary conditions

With periodic = true, every axis is periodic; pass one Bool per axis for some of them. The sum then runs over all periodic images of the sources. Points must lie in $[0, \mathrm{period})$ along the periodic axes.

Periodic sums of the Laplace potential converge only for densities with zero net charge. Their gradient (the field) is well defined, and it is invariant under shifting every point (modulo the period):

F0 = F .- sum(F) / length(F)                     # zero net charge
E1 = fmm_eval(Laplace3D_FxdU(), Xs, F0, Xt; digits = 8, periodic = true)
shift(X) = mod.(X .+ [0.3, 0.6, 0.1], 1.0)
E2 = fmm_eval(Laplace3D_FxdU(), shift(Xs), F0, shift(Xt); digits = 8, periodic = true)
maximum(abs, E2 .- E1) / maximum(abs, E1)
7.607263143976423e-9

Accuracy and cost

digits sets the multipole order of PVFMM, $m = 2\lfloor 0.55\,\mathrm{digits} \rfloor$. These relative errors were measured with 6×10⁴ uniformly random points:

kerneldigits = 6digits = 8digits = 10digits = 12
Laplace3D_FxU, Laplace3D_DxU, Laplace3D_FxdU≈ 2e-6≈ 7e-8≈ 6e-11
Stokes3D_FxU, Stokes3D_DxU≈ 2e-6≈ 7e-8

Stokes kernels reach about two digits less than requested, and Stokes3D_FxT less again. Ask for more digits if you need them.

The run time grows linearly with the number of points. On one 96-core AMD EPYC 9474F node, with 10⁶ sources and 10⁶ targets, Laplace at 6 digits takes:

threads11696
evaluation, same points [s]4.250.290.078
first evaluation, building the tree [s]4.900.660.62

A direct sum takes about 10 s on 96 threads, so the FMM is roughly 125× faster here.

Precomputation is a one-time cost per kernel and digits. It takes seconds for Laplace (≈ 20 s at 12 digits) and minutes for Stokes (≈ 1.5 min at 8 digits and ≈ 4 min at 10 digits on 16 threads). The operators are saved to SCTL.fmm_cache_dir and loaded from there afterwards.

Pitfalls

  • Precompute before parallel jobs. Several processes computing the same operator file at once may read each other's partial files. When running many independent jobs (e.g. with disBatch), run one small evaluation per kernel and digits first, so later jobs only read the cache.
  • The cache directory must exist. It is ENV["PVFMM_DIR"] if set before using SCTL, otherwise a scratch space in the Julia depot, which SCTL.jl creates. PVFMM terminates the process if the directory is missing, so do not delete the directory while Julia is running.
  • Watch the dynamic range. The accuracy is relative to the largest potential. Targets very close to sources get near-field (direct) treatment, but potentials that vary over many orders of magnitude lose relative accuracy in the smaller values.
  • Threads. The FMM uses OpenMP (OMP_NUM_THREADS, SCTL.set_num_threads). It scales well up to tens of threads; building the tree stops scaling at around 32 threads.

Reference

SCTL.ParticleFMM — Type
ParticleFMM(kernel; digits=10, periodic=false, period=1.0)

Fast multipole evaluation of the sum $U(x_t) = \sum_s K(x_t - x_s) F_s$ (SCTL's ParticleFMM<double,3> with PVFMM) for a kernel from fmm_supported_kernels: Laplace3D_FxU, Laplace3D_DxU, Laplace3D_FxdU, Laplace3D_Fxd2U, Laplace3D_DxdU, Stokes3D_FxU, Stokes3D_DxU and Stokes3D_FxT. The result is the same as kernel_eval, to accuracy digits, in O(N) work instead of O(Ns·Nt).

Set the points and density with set_sources!, set_density! and set_targets!, then call fmm_evaluate (or fmm_evaluate!). The tree is rebuilt only when points change, so evaluating new densities on fixed points (e.g. inside gmres) is the fast case. fmm_eval does all of this in one call.

  • digits: requested accuracy (relative to the largest potential). Measured: Laplace kernels reach it; Stokes kernels about 2 digits less (digits = 10 gives ≈ 1e-7); Stokes3D_FxT less again.
  • periodic: true (all axes), or one Bool per axis; the periodic box is $[0, \mathrm{period})$ along each periodic axis.

The FMM is used for 40000 or more targets, or with periodicity; smaller problems are summed directly (SCTL's choice). It needs the library built with PVFMM (SCTL.has_feature(:PVFMM)); otherwise every evaluation is a direct sum, and periodicity is unavailable. The first evaluation for a kernel and digits precomputes translation operators, cached on disk (SCTL.fmm_cache_dir).

The C++ object is freed by a finalizer, or explicitly with close(fmm).

SCTL.fmm_cache_dir — Function
SCTL.fmm_cache_dir()

Directory where PVFMM stores the operators it precomputes for each kernel and accuracy (files Precomp_*.data). Computing them takes from seconds (Laplace) to minutes (Stokes, high accuracy) the first time; later sessions load them. The directory is ENV["PVFMM_DIR"] if that is set when SCTL is loaded, otherwise a scratch space in the first Julia depot. Delete its files to force recomputation.
